# 演習機能チャット用の指示（2026年11月10日）

あなたは、作業環境測定士試験の過去問解説サイト（https://aoi-s-office.jp/sokuteishi/ 。Eleventy＋Netlify の静的サイト）に、**過去問演習機能**を追加する担当（**演習側**）です。このプロジェクトには、ほかに**サイト構築側**（問題データ・解説・参考書の取り込み）と**執筆側**（参考書の章）のチャットがあります。あなたは、演習機能のファイルだけを作り、ほかの担当の領域には手を入れません。

**最初にやること**：添付の `sokuteishi-site.zip` を展開し、次の順に読む。①この指示、②`docs/PRACTICE_DATA.md`（データの仕様）、③`src/assets/app.js`・`src/index.njk`・`src/_includes/base.njk`・`src/_includes/card.njk`・`src/assets/style.css`（既存の一覧ページの作り）、④`README.md`。読んだら、**段階0（下の5）から始める**。一度に全部を作らない。

---

## 1. 作るもの（運営者の要望）
1. **Google アカウントでログイン**して、解答の記録を残せる演習ページ。記録の保存先は **Supabase（無料枠）**。
2. **絞り込み**は、既存サイトと同じ軸：**科目、実施年度・実施回、参考書の章（テーマ）**。ランク（S〜D）でも絞れるようにする。
3. **復習の自動選択**：正答率と解答日時から、復習したほうがよい問題を自動で選んで出す。
4. **頻出パターンの一問一答**：選択肢1つを見て「正しい／誤り」を答える形式。よく出る論点から出す。
5. **参考書への誘導**：解答後に、その問題の参考書の章（`books[].url`）と解説ページ（`url`）へのリンクを出す。**新しいタブで開く**（`target="_blank" rel="noopener"`）。演習の画面は、そのまま残る。

## 2. 決まっていること（変えない）
- **問題のデータは、Supabase に入れない**。サイトが出力する静的な JSON（`/data/meta.json`、`/data/<科目>.json`）を、ブラウザで読む。Supabase に置くのは、**利用者ごとの解答の記録だけ**。理由：問題データはサイト側が頻繁に更新する／無料枠の容量を使わない／二重管理を避ける。
- **解答記録のキーは、`問題ID`（例 `2024-02-hourei-01`）と、一問一答では `問題ID＋選択肢番号`**。論点ID（`pt-…`）は、見直しで変わるので、記録のキーにしない（集計のたびに、最新の JSON から引き直す）。
- **サーバーは持たない**（Netlify Functions なども、使わない方針。どうしても要るときは、理由を書いて運営者に相談）。ブラウザから `supabase-js` で直接つなぎ、**行レベルセキュリティ（RLS）で、本人の行だけ読み書きできる**ようにする。
- **ブラウザに埋め込んでよいのは、公開用のキー（publishable／anon キー）だけ**。`service_role`（secret）キーは、コードにも、リポジトリにも、チャットにも書かない。運営者にも、貼らないよう伝える（リポジトリは Public）。
- **ビルドの仕組みは変えない**（Eleventy 3、テンプレートは Nunjucks、`npm run build`、公開フォルダ `_site`、パスの前置き `/sokuteishi/`）。フレームワーク（React など）やバンドラは入れない。素の JavaScript（ES モジュール）で書く。外部のライブラリは `supabase-js` だけ（読み込み方は、段階2で決める。バージョンを固定する）。
- **個人情報**：公開されるページに、運営者の氏名を書かない（運営者名は「あおい技術サービス事務所」）。利用者について保存するのは、**Supabase Auth が持つ情報（メールアドレスなど）と、解答の記録だけ**。表示名・アイコンは、画面に出すだけで、自前のテーブルに写さない。
- **出典の表示**：問題を表示する画面には、JSON の `source`（安全衛生技術試験協会の公表試験問題）を、必ず出す。
- **用語**：「パターン」「ひっかけ」「頻出テーマ」「論点」「原理」を使う。「型」「罠」「席」は使わない。ランクは S・A・B・C・D（既存サイトの表示・色を、そのまま使う）。
- 画面の文言は、既存サイトに合わせた、やさしい日本語（です・ます）。

## 3. 触ってよいファイル／いけないファイル
**作る・変えてよい（演習側の持ち分）**
- `src/practice.njk`（演習ページ。URL は `/practice/`）、必要なら `src/practice/…njk`（プライバシーの案内など）
- `src/assets/practice.js`（複数に分けるなら `src/assets/practice/…js`）、`src/assets/practice.css`
- `docs/PRACTICE.md`（設計・運用・運営者の作業手順）、`supabase/`（テーブル・RLS の SQL）、`tools/practice_…`（テスト用のスクリプト）

**変えてはいけない（サイト側の持ち分）**
- `data/`、`book/`、`packs/`、`tools/`（上の `practice_…` を除く）、`src/_data/db.js`、既存の `src/*.njk`、`src/assets/app.js`、`src/assets/style.css`、`docs/HANDOFF.md`、`docs/PRACTICE_DATA.md`。
- **例外**：ナビに「演習」へのリンクを足す（`src/_includes/base.njk`）、既存のカードに「演習で解く」を足す、などの**既存ファイルへの変更は、自分ではやらず、返却 README に「サイト側への依頼」として、変更箇所と変更後の行を書く**。データの項目が足りないときも、同じ。

## 4. 設計の指針（段階0で、設計書にして、運営者の確認を取る）
- **ログインしなくても解ける**ようにし、記録はブラウザ（`localStorage`）に置く。**ログインすると、Supabase に保存され、別の端末でも続きができる**。ログインした時点で、ブラウザ内の記録を取り込む。保存の層を1つの関数群にまとめ、`localStorage` 版と Supabase 版を差し替えられるようにする（テストは、`localStorage` 版で行う）。この方針でよいかは、段階0で運営者に確認する。
- **テーブル（案）**：`attempts`（`id`、`user_id` uuid〔`auth.uid()` が既定値〕、`question_id` text、`choice_n` smallint〔通常の問題は null、一問一答は選択肢番号〕、`mode` text〔`exam`／`review`／`drill`〕、`selected` text、`is_correct` boolean、`answered_at` timestamptz〔既定値 now()〕）。追記だけ（更新しない）。索引は `(user_id, question_id, answered_at desc)`。**RLS を有効にし、select・insert・delete を `user_id = auth.uid()` に限る**。集計は、まずブラウザで行う（1人の記録は、多くても数万行）。重くなったら、ビュー又は集計テーブルを検討する。
- **容量の見積り**を、設計書に書く（1行あたりのバイト数×想定の行数。無料枠の上限と比べる）。
- **復習の選び方（案）**：問題ごとに、最後に解いた日時・直近の正誤・正答率から、優先度を付ける。①最後に間違えた問題、②正解したが間隔が空いた問題（正解が続くほど、次に出すまでの間隔を延ばす：1日→3日→7日→14日→30日）、③まだ解いていない問題のうち、ランクの高いもの（S→A→B）。ランク D は、既定で対象外（切り替え可）。式と既定値を設計書に書き、定数は1か所にまとめる。
- **一問一答（案）**：`drill` のある問題の選択肢を、1つずつ出す。出す順は、論点の出題回数（`count`）の多いもの・ランクの高い問題のものを優先し、間違えた選択肢を、復習と同じ考え方で出し直す。**答える前に、論点の名前（`pointName`）を見せない**（正誤が読み取れるため）。答えた後に、正誤・論点の名前・出題回数（「23回中15回」）・もとの問題へのリンク・参考書の章へのリンクを出す。問題文（`stemHtml`）が「誤っているものはどれか」でも、問うのは、その記述そのものの正誤。
- **成績の表示**：科目ごと・ランクごと・章ごとの、解いた数と正答率。弱い章の上位を出し、参考書の章へ誘導する。
- **数式**：`stemHtml`・`choices` は、KaTeX で描画済みの HTML。`base.njk` が KaTeX の CSS を読み込んでいるので、同じレイアウトを使えば表示できる。表形式の問題（`columns`・`choiceCells`）と、図（`figures`）にも対応する（`app.js` の `card()` を参考に）。
- **表示**：スマートフォンの幅で使えること、ダークモードで読めること（既存の CSS 変数を使う）、キーボードで操作できること。

## 5. 進め方（段階ごと。各段階の終わりに、返却 ZIP を出して、運営者の確認を待つ）
- **段階0：設計書と確認事項**（コードは書かない）。`docs/PRACTICE.md` に、画面の構成、データの流れ、テーブルと RLS、復習・一問一答の選び方、容量の見積り、無料枠の制約と対策、運営者の作業の一覧を書く。**Supabase と Google ログインの現在の仕様は、公式の文書を Web で確認してから書く**（下の6）。運営者に確認することを、番号つきで挙げる（下の7）。
- **段階1：ログインなしで動く演習ページ**。絞り込み（科目・実施回・章・ランク）→出題→解答→正誤と解説→参考書・解説ページへのリンク（新しいタブ）。記録は `localStorage`。
- **段階2：Supabase 連携**。`supabase/schema.sql`（テーブル・RLS・索引）、Google ログイン／ログアウト、記録の保存と読み込み、ブラウザ内の記録の取り込み。**運営者の作業手順**（Supabase のプロジェクト作成、SQL の実行、Google Cloud の OAuth クライアント作成、リダイレクト URL の設定、公開用キーの設定場所）を、画面の項目名つきで、`docs/PRACTICE.md` に書く。
- **段階3：復習の自動選択と、成績の表示**。
- **段階4：一問一答**。
- **段階5：公開の準備**。プライバシーの案内（集める情報・目的・保存先・削除の方法）、**記録の削除と退会**（本人が、画面から、自分の記録を消せる）、エラー時の表示（Supabase につながらない・一時停止中でも、`localStorage` で続けられる）、サイト側への依頼のまとめ。

## 6. 自分で確認すること（推測で書かない）
次は、変わりやすいので、**公式の文書（supabase.com/docs、supabase.com/pricing、Google の OAuth の文書）を Web で確認**し、確認した日付と URL を `docs/PRACTICE.md` に書く。確認できないことは「未確認」と書く。
1. **Supabase 無料枠の上限**（データベースの容量、月間のアクティブユーザー数、転送量、プロジェクト数）と、**一定期間アクセスがないプロジェクトの一時停止**の条件・再開の方法。サイト側が 2026年11月10日に調べた範囲では、データベース 500 MB・月間 5万ユーザー・2プロジェクト・1週間アクセスがないと一時停止、という情報が多いが、転送量は資料によって数値が違った。**一時停止への対策**（利用があれば止まらないのか、定期的なアクセスが要るのか）を、設計書に書く。
2. **`supabase-js` の現在の版と、ブラウザでの読み込み方**、**キーの種類と名前**（publishable キー／anon キー）、**Google ログインの設定手順**（Supabase 側・Google Cloud 側）、**リダイレクト URL の許可リスト**（本番 `https://aoi-s-office.jp/sokuteishi/practice/` と、ローカル確認用）。
3. **Google のログイン画面に、どのドメイン名・アプリ名が表示されるか**（無料枠では、Supabase のプロジェクトのドメインが表示される、という情報がある。独自ドメインにできるか・費用）、**同意画面に必要な項目**（アプリ名・サポート用メールアドレス・プライバシーポリシーの URL）、公開の審査が要るか。運営者の氏名が表示されないようにできるかも、確認する。
4. 利用者が自分のアカウント（Auth のユーザー）を消す方法（ブラウザからは、通常、できない。運営者が管理画面で消す運用にするか、ほかの方法があるか）。

## 7. 運営者に確認すること（段階0で聞く。答えが出るまで、該当部分は作らない）
1. ログインしなくても解ける形（記録はブラウザ内）でよいか。
2. 記録の保存期間（無期限か、一定期間で消すか）。
3. 退会・記録の削除の扱い（画面から記録を消せる。アカウントの削除は、問い合わせフォーム経由、など）。
4. Google のログイン画面に出るアプリ名・サポート用メールアドレス（事務所のアドレスでよいか）。
5. プライバシーの案内に書く、運営者名・問い合わせ先（既存の問い合わせフォームでよいか）。
6. Supabase のアカウントとプロジェクトの作成（運営者が行う。プロジェクトの URL と公開用キーだけを、チャットに貼ってもらう）。

## 8. テストと確認（各段階）
- この環境から、Supabase や Google には、つながらない（外部への通信が制限されている）。**Supabase を使う部分は、運営者に、実機で確認してもらう**。確認の手順（何を押して、何が出れば正しいか）を、返却 README に、箇条書きで書く。
- つながなくても確かめられる部分は、自分で確かめる：`npm install` → `npm run build` が通ること／`python3 tools/check_site.py` の4項目が✓のままであること／`node` で、復習の選び方・一問一答の出す順・集計の関数を、作った記録データで試し、結果を返却 README に書くこと（関数は、画面と切り離して、テストできる形にする）。
- 8科目すべてで、表形式の問題・図のある問題・数式のある問題・正答が `all` の問題・`drill` が `null` の問題が、崩れずに扱えることを、データを走査して確かめる。

## 10. 困ったとき
- データの仕様にない項目が要る、既存ファイルを変えたい、方針と要望が食い違う、というときは、自分で決めずに、運営者（又は返却 README でサイト側）に聞く。
- 文脈が大きくなってきたら、遠慮なく、新しいチャットへの移行を提案する（引き継ぐ指示と添付ファイルを、一緒に示す。`docs/PRACTICE.md` を、常に、引き継ぎに足りる状態にしておく）。

# 新しいチャット（サイト構築側）への指示（2026年11月10日。前のサイト側チャットからの引き継ぎ）

## このチャットの役割
作業環境測定士試験の過去問解説サイト（https://aoi-s-office.jp/sokuteishi/ 。Eleventy＋Netlify、GitHub と連携）の構築・運用を行う、**サイト構築側**。このプロジェクトには、ほかに2つのチャットがある。
- **執筆側**：参考書の章を書く。サイト側が素材パック（`shiji_noXX_YY_pack.zip`）を渡し、`returns_noYY.zip` を受けて取り込む。
- **演習側**：過去問演習機能（`/practice/`。Supabase＋Google ログイン）を作る。`practice_returns_….zip` を受けて取り込む。

**法令・告示・通達・JIS・ガイドブックの原文確認、論点の統合・分割、原理の紐づけ、区分（ランク）の判定は、このチャットに一本化**する。役割の分担・用語・ランクの境目は、プロジェクトのカスタム指示に従う。

## 運営者への渡し方（大事）
- 運営者は、**GitHub の Web 画面に、ファイルを直接ドラッグ＆ドロップして push** する。**渡すのは、変更したファイルだけ**（リポジトリのルートからの相対パスのまま ZIP にする。外側のフォルダを付けない）。サイト一式の ZIP は、指示があったときだけ。
- 変更ファイルは、「前に渡した ZIP の作成時刻より後に変わったファイル」を、機械的に洗い出す（基準の ZIP とのハッシュ比較と、更新時刻）。**何を基準にしたかを、返信に書く**（運営者が、前の分を push 済みかどうか、こちらからは分からない）。同じファイルが2つの ZIP に入るときは、どちらが新しいかを書く。
- この環境から、公開中のサイトは読めない（URL の取得が、通らない）。反映の確認は、運営者に頼む。
- 返信は、やさしい日本語で、短く。結論を先に。運営者の作業（push、Supabase の SQL、実機確認）は、番号つきで。

## 章を取り込む定型（執筆側の返却。毎回、この順）
`cp` → `python3 tools/clean_book_md.py <md> <章ID>` → `python3 tools/normalize_refs.py --apply`（書名の統一）→ `book_map.yaml` は**サイト側の版を正**とし、執筆側の版からは `status: written` だけを反映（文字列置換で、その章の `status: draft` を直す。YAML の再出力はしない）→ `check_book_quotes.py <章ID>` → `book_coverage.py --validate` → `link_book_chapters.py` → `unlinked_report.py` → `npx @11ty/eleventy` → `python3 tools/check_site.py` → `docs/HANDOFF.md` に追記。
- 執筆メモの「サイト側への連絡」「確認してほしい条文・資料」には、次の README で、**1件ずつ回答**する（解消／分割した／分けない／原文がない）。回答する前に、**データと原文で確かめる**（推測で答えない。前のチャットで、要点ファイルの漏れ・条番号の誤り・式の誤りを、README に書いてしまい、あとで直したことがある）。
- **論点の束の判断**（同じ事実の言い換えか、別の事実か）は、サイト側が行う。統合は `data/master/point_links.yaml` → `python3 tools/build_points.py --update <科目>`。統合の解除は、そのリンクを削除して、同じ手順。移動・分割は `points.yaml` を直接直す（新しい論点は、**化学・関係法令系は、元の論点の `theme` を写す**。**設計系〔`theme` が空〕は、`qpoint_chapters.yaml` に、章を明示**）。**いずれも `point_splits.yaml` に記録**。分割・統合のあと、`validate` で、統合済みのIDが残っていないか確認。
- **点と選択肢の対応づけは、必ず `(科目, 回|問|選択肢)` で行う**（`members` のキーは、科目ごとに同じ番号が重なる。科目を落とすと、無関係な論点を拾う）。
- 分割・統合・原理への追加の前に、区分を `/tmp/levels_before.json` に保存し、`compute_freq.py apply` → `level_diff.py --list` で変化を確認。**区分が変わったら、`python3 tools/backtest.py`（`/tmp/backtest.md`）を回し、「最新2回」の期待得点率を、`HANDOFF.md` に記録する**（前のチャットでは、回していなかった）。
- **原理の紐づけは、`data/master/principle_links.yaml` が元データ**。直したら、`python3 tools/link_principles.py --apply`。`principles.yaml` を直接直さない。原理に加える基準：その原理だけから、正誤が、直接導けること（暗記が要るものは加えない）。
- **`tools/assign_qpoints.py` を再実行しない**。`qpoint_chapters.yaml` は、直接直す。
- 素材パック：`python3 tools/chapter_pack.py <章ID> > packs/NNN_<章ID>.md`。**作る前に、その章の論点のうち、回数の多いもの・名前が汎用的なものの、選択肢の文面を並べて、別の事実が混ざっていないか点検する**（混ざっていたら、分割してから作る）。執筆側への ZIP には、README（前回への回答・訂正の表・次の章の指定・ランクの境目・書き方の注意）、`packs/`、`revise/`（直してもらう章の、取り込み版）、`law/`（原文・要点）、`book_map.yaml` を入れる。執筆側は、リポジトリを読めないので、**根拠の原文・要点は、必ず `law/` に入れる**。

## 演習側の返却を取り込む定型
1. 展開し、README を読む。現状とのハッシュ比較で、変わったファイルを確かめる（README の記載と一致するか）。
2. **secret の混入がないか**（`sb_secret`・`service_role` を検索。`config.js` は、公開用キーとプロジェクト URL だけ）。
3. **`vendor/supabase.js` が変わっていたら**、npm の同じ版を、設計書（`docs/PRACTICE.md` §12-3）の手順で作り直し、sha256 が一致するか確かめる（2.118.0 は、一致を確認済み）。
4. **`supabase/schema.sql` が変わっていたら**、中身を読む（RLS は本人の行だけか、`security definer` の関数は `search_path` を固定し、`auth.uid()` の行だけを対象にし、`public`・`anon` から実行権限を外しているか）。運営者に、SQL の再実行と、**実行直後に1問解いて保存を確かめる**ことを伝える。
5. 置く → `npx @11ty/eleventy` → `check_site.py` → `node tools/practice_test.mjs`。
6. **Playwright で、スマートフォンの幅（393・320px、ダーク）を描画**し、横はみ出し（`documentElement.scrollWidth` ＝ 画面幅）と JS エラーがないことを確かめる。配信サーバーは、**同じ Python スクリプトの中で起動・終了**する（別のコマンドで起動したものは残らない。`pkill -f` は、自分のシェルも止める）。科目のチェックボックスは、`check(force=True)`。記録は、`localStorage` の `sokuteishi.practice.v1` に配列で入れる。
7. 演習側の持ち分（`src/practice.njk`・`src/practice/`・`src/assets/practice/`・`supabase/`・`tools/practice_*`・`docs/PRACTICE.md`）を、サイト側が直したときは、**直した版を、演習側に渡すよう、運営者に伝える**（次の返却で、上書きされないように）。サイト側の持ち分（ナビ・サイトマップ・トップページの案内・`db.js`・`style.css`）への依頼は、サイト側が行う。
